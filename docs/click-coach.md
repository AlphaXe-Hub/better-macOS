# 点击教练（Click Coach）

> 目标：让用户从「点菜单」迁移到「用快捷键」。
> 做法：在他**用鼠标点菜单项**的那一刻，告诉他这件事有快捷键。

## 为什么是这个时机

迁移期用户还没在用快捷键，所以「按键吐司」和「快捷键面板」都使不上劲——
前者要等他按下去才教，后者要他自己知道去查。

而他用鼠标点「文件 → 存储」时，**意图是最明确的**（我要存储），
答案（⌘S）就在他手指旁边。这一刻的教学效率最高，过期作废。

## 为什么只认菜单项

这是实测结论，不是设计偏好（2026-11-08 实测，macOS 26.5）：

| 目标 | 能拿到什么 | 结论 |
|---|---|---|
| 菜单项 | 命中 `AXMenuItem`，`AXMenuItemCmdChar` + `AXMenuItemCmdModifiers` 直接给出快捷键 | ✅ 不需要猜 |
| 工具栏按钮 | 枚举文本编辑与访达整棵 AX 树，`AXButton` / `AXPopUpButton` 的 title/description/help **全空** | ❌ 自绘图标，无标签 |
| 普通控件 | 无语义动作 | ❌ 不做 |

工具栏按钮没有无障碍标签，想把「这个按钮 = ⌘B」对上只能靠猜位置或猜名字。
**猜错比不说更伤**——用户一旦发现教错了，就不会再信任这个工具的任何提示。
所以覆盖范围刻意收窄到菜单项：**宁可不教，不可教错**。

## 为什么必须用 CGEventTap

这是最容易踩错的一处，实测对比：

| 方案 | 普通点击 | **菜单展开时点击** |
|---|---|---|
| `NSEvent.addGlobalMonitorForEvents` | 能收到 | **一条都收不到** |
| `CGEvent.tapCreate(.cgSessionEventTap, .listenOnly)` | 能收到 | **能收到** |

菜单展开时 AppKit 进入自己的模态跟踪循环，NSEvent 全局监听在这段时间**完全静默**。
而「点菜单」正是这个功能唯一有效的场景——那条路等于整个功能不可用。

两个细节：
- `.listenOnly`：只旁听，不改写事件。教练永远不替用户做决定。
- `CFRunLoopAddSource(..., .commonModes)`：只注册 `default` mode 的 source
  在菜单跟踪期间是停摆的，和上面同一个根因。

## 为什么同步查询

命中测试实测耗时（探针即 App 内置的 `--click-at`，见文末自测）：

```
普通区域：平均 0.61 ms，中位 0.36 ms，p95 0.58 ms，最大 25.91 ms（首次调用）
菜单项：  平均 0.31 ms，最大 0.64 ms
```

同步做保证**确定性**：事件到达时菜单一定还开着。异步哪怕延迟 20ms，
菜单可能已经因为别的操作关闭，查询就落空。0.3ms 用户完全无感。

## 衰减

同一个 `(App, 动作)` 最多教 **3 次**，之后彻底静默。

- 通常第 2 次就记住了，第 3 次是冗余
- 反复弹会变成噪音，用户会直接关掉整个功能——那时连有用的提示也没了
- 计数按 `(App, 动作)` 分开：⌘N 在访达是「新建窗口」、在文本编辑是「新建文档」

## 边界（说清楚，不假装）

- **只看菜单项**。工具栏按钮、右键菜单里没绑快捷键的项、普通控件，一律沉默。
- **只在自己有辅助功能权限时工作**。没有权限就不装 tap，不是装个假的。
- **不记录点击历史**。计数只在内存里，重启即清零；不写盘、不上报。
- **不改写事件**。`listenOnly`，用户点下去的就是他要的。

## 自测

```bash
./app/test.sh                                  # 285 项，含组合串解码与衰减常量
./app/build/better-macOS.app/Contents/MacOS/better-macOS --click-at 210 51
```

`--click-at` 在指定屏幕坐标跑一次命中判定并打印结果，不依赖真实鼠标。
它**必须在 `NSApplication` 初始化之前**处理，否则进程会挂进事件循环不退出。
