## 已确认的决策

### D1 定位：先服务自己，UI 按普通人标准
**决策**：v1 的目标用户是「作者本人 + 同类开发者」；但按键吐司这种面向新手的呈现不能省。
**理由**：一个人做，产品化最大成本是「免砸坑引导」，不是功能。先让自己每天爽。
**后果**：不做多语言、不做引导向导、不做崩溃上报；但也不能出现「只有作者懂的开关」。

### D2 产品形状：一个 App、两层能力
**决策**：单个菜单栏 App，功能分两层：
- **L1 学习层**：吐司 HUD + 快捷键速查面板/浏览器。只读系统，零写入风险。
- **L2 修正层**：自然滚动分离等开关。每个独立可控、可一键还原。

**理由**：N 个功能 = N 倍权限矩阵 + N 倍兼容性 bug。两层是两种完全不同的技术域，模块必须分开。
**后果**：L2 每个开关都必须自带「还原到系统默认」，否则用户不敢开。

### D3 吐司语义：v1 只做「确认型」
**决策**：v1 只回答「你刚触发了什么动作」（KeyStruck 同款）。「Windows 上这是哪个键」的教学型提示（B）作为差异化钩子放进路线图，不进 v1。
**理由**：A 只读系统真相，零维护零出错；B 需要一张 macOS 没有的「动作↔双平台键位」映射表，是独立的数据工程。
**后果**：v1 与 KeyStruck 功能重叠度高，需要靠其他点差异化（见 D4、D7）。

### D4 滚动分离：v1 只做「独立反转」，当样板间
**决策**：只做垂直方向 + 鼠标/触控板独立，不做横向/加速度曲线/平滑度。把它做成 L2 其他开关可照抄的模板。
**理由**：完整版已被 LinearMouse（免费开源）做完；本功能的价值是验证「一个痛点 → 一个开关 → 一键还原」的产品骨架。
**后果**：必须做到「比系统设置更清楚、比 LinearMouse 更傻瓜」。

### D5 完成定义：先本机可跑，发布走 GitHub + DMG
**决策**：v1 验收标准 = 本机 `open` 即用的 App。发布形态 = **GitHub Releases 提供 DMG 安装包**。
**理由**：Mac App Store 的沙箱 + 输入监控 + AX 组合基本走不通；无签名证书时 MAS 路线直接不可行。
**后果**：必须解决 Gatekeeper（用户首次打开需右键/去隔离属性）、以及「无公证时 Sparkle 更新怎么办」。这些是发布前必须回答的开放问题。

### D6 仓库结构：单仓库三分
**决策**：`app/`（代码）+ `research/`（研究事实）+ `docs/adr/`（决策）。MIT 协议保留。
**理由**：研究与代码同仓，AI 与人都能一眼看到「为什么这么做」。
**后果**：`research/` 里的结论必须带出处，否则半年后没人敢信。

## 未定项（下一轮盘问）

- **数据来源**：「动作 ↔ 双平台键位」映射表从哪来？手工维护？从 Windows 官方文档抓？社区众包？
- **模块接缝**：L1 的「读取前台 App 菜单」这件事，接口应该长什么样？（深模块：小接口 + 厚实现）
- **权限引导**：AX / Input Monitoring 要几个开关？未授权时降级成什么样？
- **开源与收费边界**：MIT 全开源，还是有付费成品？
- **发布流水线**：无证书 → DMG 怎么签？Sparkle 要不要？Homebrew Cask 要不要上？
- **视觉语言**：KeyStruck 的毛玻璃胶囊是「Mac 原生」路线；要不要做成「Windows 迁移者友好」的另一种视觉（更明确、更像教学卡）？

| 项 | 事实 |
|---|---|
| 系统 | macOS 26.4 arm64（Tahoe） |
| 编译器 | Swift 6.3.3（CLT），SDK 26.5 |
